## 2. 可复用经验摘要（按记忆规则格式整理，待共享目录确认后经 memory.py 入库）

**主题**：产品方案类规格的阶段 0 规划拆解方法（前置调研 + 矛盾点处理）
**适用条件**：用户交付的是 AI 协助撰写的"产品方案 + 分阶段开发提示词"类文档，需要先做规划再编码时。
**常见陷阱**：
1. 方案自带的技术选型（如"X 或 Y 二选一"）常按当时的流行度写成，开源组件维护状态可能已变化——规划期必须实测核验，不能沿用方案的静态陈述。
2. 方案中"阶段划分"（开发视角）与"优先级分级"（交付视角）可能互相冲突（如阶段 3 含 P1 模块），不处理会在验收时产生争议。
**易误解项**：npm 仓库"有活动"≠"npm 包在更新"（本次案例：frappe/charts 仓库 2026-10 仍有推送，但 npm 最新版停在 2021-06——须分别查 registry 发布时间与仓库 pushed_at）。
**拆解模式**：
1. 阶段 0 先用 GitHub API（`/repos/{owner}/{repo}`：license/pushed_at/stars）+ npm registry（`/{pkg}/latest`：version/发布时间戳）实测核验，再写架构结论。
2. 阶段与优先级冲突时的处理模板：阶段顺序保留（提示词明确列入的实施位置不变）、任务加 [P1] 标记、验收清单不含被延后项、用户可整体裁剪——形成"P0 最小路线"与"全量路线"两个数字。
3. 社区 wrapper 停更时的处理：核验其锁定依赖（本例 react-frappe-gantt 锁 frappe-gantt@0.5.0+react16），确认不可用后转为"主库依赖 + 自研薄封装"任务，工作量 1-1.5h 级别。
**事实依据**：2026-10-10 对 frappe/gantt、frappe/charts、opf/openproject、makeplane/plane、taigaio/taiga（及 taiga-back/front）API 实测；npm 上 frappe-gantt@1.2.2/frappe-charts@1.6.2/react-frappe-gantt@0.2.3/antd@6.6.5/echarts@6.1.0 的版本与发布时间。
**实际结果**：规划包 10 份文档一次成稿；工时逐项求和核对一致；矛盾点 C-1~C-6 均给出处理意见。（后续实施反馈后更新效果。）
**状态**：待验证（规划方法已应用一次；待阶段 1-6 实际执行反馈后晋升）
