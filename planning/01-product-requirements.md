## 1. 产品概述

### 1.1 定位（方案·引言）

> "把产品定位为：个人项目经理的 AI 项目交付工作台。重点不是做一个缩小版 Microsoft Project，而是将项目计划、实施过程、风险问题、交付资料和 AI 助手整合到一起，并通过 Docker 部署在自己的服务器上。"

**使用形态**：个人使用的中文 PC Web 应用（阶段 0 提示词："以中文 PC Web 应用为主"）。
**部署形态**：Docker Compose（已确认目标环境为本地 Windows 电脑的 WSL2 Ubuntu 26.04，x86_64）。
**核心数据**：项目、任务、风险、资料（方案·一「最终产品范围」表）。

### 1.2 两条设计铁律（方案·引言，优先级高于一切功能）

- **BR-G1 业务数据由系统管理**：项目管理业务数据必须由系统可靠管理（数据库为唯一事实来源），AI 负责辅助，不负责充当数据库或项目事实来源。
- **BR-G2 闭环优先**：先把一个项目从启动、计划、实施、风险处理一直管理到验收收尾的闭环跑通，再扩展更多工具。

### 1.3 用户与场景

- 单用户（个人项目经理本人），无需多用户权限体系（多用户协作属 P2，方案·一）。
- 典型场景：管理信息化集成项目的 WBS、进度、风险、问题、干系人与交付资料；借助 AI 生成 WBS 初稿、风险建议与周报初稿，人工确认后落入业务台账。

## 2. 功能范围与优先级（范围基线）

### 2.1 优先级定义（方案·一「功能分级」表原文）

> "P0 是第一版必须完成的功能，P1 应在核心闭环稳定后纳入，P2 暂时不应成为开发阻塞项。"

| 优先级 | 功能范围 | 目标（原文） |
|---|---|---|
| P0 | 项目管理、WBS、任务依赖、甘特图 | 建立完整的计划管理能力 |
| P0 | 风险、问题、里程碑、进度快照 | 建立实施过程跟踪闭环 |
| P0 | AI 助手、WBS 生成、风险分析、周报生成 | 第一版就能实际使用 AI |
| P1 | 干系人管理、交付资料清单、Excel 导入导出 | 覆盖常见交付管理工作 |
| P1 | 文档模板、Word 报告生成、项目收尾 | 减少重复制作项目资料 |
| P2 | 多用户协作、复杂审批、移动端、外部系统集成 | 未来按需扩展 |

补充限定（方案·一）："第一版的 AI 必须集成，但不必自建大模型。应优先通过可配置的模型 API 接入服务，同时保留未来接入本地模型的能力。"

## 6. 范围边界（明确排除项）

1. **不做微服务**：第一版采用前后端分离、模块化单体（方案·二："不要急着拆微服务"）。
2. **不引入**：Redis、消息队列、独立向量数据库、Kubernetes（方案·二："除非后续需求明确证明它们有必要"）。
3. **不做多租户 / 企业级权限体系**（阶段0提示词："避免过早引入……企业级多租户体系"）。
4. **不自建大模型**（方案·一："不必自建大模型"）。
5. **P2 功能全部除外**（方案·一："P2 暂时不应成为开发阻塞项"）。
6. **不复制 GPL/AGPL 项目代码**：OpenProject（GPL-3.0）、Plane（AGPL-3.0）、Taiga 仅借鉴交互与业务设计，不引入代码（方案·三；详见 02 文档）。

## 7. 与既有《项目验收资料文件管理系统》的关系说明
